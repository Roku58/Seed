## 1. これは何か

Seed.UI は「画面の登録・レイヤ別の切替・戻り履歴・出入り演出」だけを引き受ける小さな基盤です。

これが無いと、画面遷移は次のように壊れていきます。

- 「リザルトを出す」コードが戦闘ロジックの中に直書きされ、リザルト画面クラスへの参照が戦闘側に漏れる（画面を差し替えるたびに戦闘コードを触ることになる）
- 「戻る」の実装が画面ごとにバラバラになり、「タイトルに戻ったのに Back でインゲームへ戻れてしまう」ような履歴バグが出る
- ポーズメニューの上に確認ダイアログを重ねたとき、どちらを先に閉じるかの管理が場当たりになる

Seed.UI では、画面の実体（クラス・GameObject）を知っているのは UI 基盤だけです。他の基盤は `ScreenId`（ただの int を包んだ共有ID）だけを知り、`hub.PublishCommand(new ShowScreenCommand(id))` と「依頼」します。処理者は `UISystem` ただ1つ——これが三大規約の「命令の処理者は1基盤」です。

> 📖 **用語 — `ScreenId`（本プロジェクト固有）**: 境界を越えて画面を指すための `readonly struct`。中身は int 1個で、`0 = ScreenId.None` は「画面なし」の予約値（有効値は1以上）。値の割り当て（1=HUD、2=リザルト…）は UI 基盤ではなく**アプリ側の定数クラス**（`Sample_ScreenIds` など）が持ちます。

> 📖 **用語 — readonly struct**: C# の「生成後に書き換えられない値型」。メッセージや ID をこれで作ると、受け取った側が中身を書き換えて他の購読者に影響する事故が構造的に起きません。

なお、この基盤は**プレハブのロード戦略を持ちません**。「登録済みインスタンスの切替」だけに絞っており、ロードが必要なら外側で読み込んでから `Register` します。

## 2. 全体像

### 部品表

| 部品 | 種類 | 役割 |
|---|---|---|
| `UISystem` | 純C#・`IDisposable` | Hub との接続点。`ShowScreenCommand` / `CloseScreenCommand` の唯一の処理者 |
| `ScreenRouter` | 純C# | 交通整理の本体。レイヤ別切替・履歴・演出の駆動 |
| `UIScreen` | abstract MonoBehaviour | 画面1枚の基底。アプリが継承する |
| `IScreenTransition` | 純C#インターフェース | 出入り演出の契約（`IsDone` / `Tick` / `Complete`） |
| `ScreenId` / `ScreenLayer` / `ScreenTransition` | 契約（`Seed.Hub.Contracts`） | 境界を越える共有語彙 |
| `ShowScreenCommand` / `CloseScreenCommand` | 命令（`readonly struct`） | どの基盤からでも発行できる遷移依頼 |

> 📖 **用語 — IDisposable**: C# の「後片付けの契約」。`Dispose()` を呼ぶと保持していた資源（ここでは Hub への購読）を解放します。`UISystem` はフェーズ退場時に Dispose される前提です。

### データの流れ

```
発行者（どの基盤でも）
  │ hub.PublishCommand(new ShowScreenCommand(id, transition, payload))
  ▼
UISystem（SubscribeCommand で受信 = 処理者1基盤）
  │ _router.Show(id, transition, payload)
  ▼
ScreenRouter（レイヤ判定・履歴操作）
  │ 前画面: BeginHide → OnHide 即時 → 抜け演出（あれば）
  │ 次画面: BeginShow → SetActive(true) → OnShow 即時 → 入り演出（あれば）
  ▼
UISystem.Tick(実時間dt) が毎フレーム演出を進め、完了時に前画面を非表示化
```

### 3レイヤの違い（具体例で）

| レイヤ | 同時枚数 | 具体例 | 閉じ方 |
|---|---|---|---|
| Base | 1枚だけ | タイトル、戦闘HUD、リザルト | `Close` では閉じない。`Back()` か次の `Show` で遷移 |
| Overlay | 複数可 | ミニマップ、通知バー | `Close(ScreenLayer.Overlay)` で**全部**閉じる |
| Modal | LIFO スタック | ポーズメニュー→その上に「本当に終了？」確認 | `Close(ScreenLayer.Modal)` で**最前面の1枚**が閉じる |

> 📖 **用語 — LIFO（後入れ先出し）**: 最後に積んだものを最初に取り出す構造。Modal はこれで、「ポーズ→確認ダイアログ」と重ねたら、閉じる順は必ず「確認→ポーズ」になります。

- **Base** は「今どの場面か」を表す土台です。戻り履歴を持つのはこのレイヤだけで、HUD→メニューと Push で進めば `Back()` で HUD へ戻れます。
- **Overlay** は Base の上に常駐する飾りです。Base を切り替えても Overlay は消えません。同じ Overlay を二重に `Show` しても無視されます（重複表示にならない）。
- **Modal** は「入力を奪う前面」です。ただし基盤は入力を止めません——アプリが `Router.ModalCount > 0` を見て操作を止めるのが役割分担です（詳細は §6・§7）。

## 3. 動かして試す

1. Unity エディタで新規シーンを作成します（Hierarchy は空で構いません。カメラ・ライトは Runner が無ければ自動生成します）
2. Hierarchy で右クリック → Create Empty で空の GameObject を作成し、Inspector の Add Component から `Sample_GameFlowRunner`（`Assets/Script/App/Samples/Sample_GameFlowRunner.cs`）をアタッチします。シーンへの事前配置はこれ1つだけです
3. Play を押します。画面にホームのテキスト（`Sample_TextPanel` の OnGUI 表示）が出ます
4. **[1] を押して出撃** → `Sample_BattlePhase.OnEnter` が `ScreenRouter` / `UISystem` を組み立て、`Sample_HudScreen` と `Sample_ResultScreen` の GameObject を生成 → `UISystem.Register` → `PublishCommand(new ShowScreenCommand(Sample_ScreenIds.BattleHud))` で HUD を表示します
   - **Hierarchy で確認**: `Stage_...` の下に `Sample_HudScreen` と `Sample_ResultScreen` が現れます。HUD はアクティブ、**リザルトは Register 直後なので非アクティブ（SetActive(false)）**です
   - **画面で確認**: 左上に「プレイヤー名 HP x/y    敵名 HP x/y」の行と操作説明行が出ます
5. 戦闘中 [1] で攻撃します。攻撃・被弾のたび HP 表示が減ります——これが `CharacterDamaged` 通知の Hub 購読による HUD 更新の実物です
6. どちらかの HP が尽きると `Sample_ReactionPolicy` が `ShowScreenCommand(Result, ScreenTransition.Replace)` を発行し、HUD が消えて中央に大きく（fontSize 40）「討伐成功！   [B] ホームへ」または「力尽きた…   [B] ホームへ」が出ます
7. [B] でホームへ戻ります。フェーズ退場で舞台ごと破棄されるため、Hierarchy から `Stage_...` と画面が消えます

うまくいかないときの Console: 未登録 ID を Show すると `Screen#n は未登録の画面（Register漏れかIDの打ち間違い）`、二重 Register は `Screen#n は登録済み（画面IDの重複）` という `HubException` が出ます。

> 📖 **用語 — OnGUI**: Unity の即時モード GUI。毎フレーム描画コードを呼ぶ古い仕組みで、デモの最小表示に使っています。実プロジェクトでは uGUI（Canvas ベース）や UI Toolkit の画面に置き換える前提です。

## 4. コードで使う

### 最小例 — 新しい画面を1枚作る（3点だけ）

```csharp
// 1) 画面クラス（ScreenId の値割り当てはアプリの定数クラスに置く）
public sealed class MyScreen : Seed.UI.UIScreen
{
    public override ScreenId Id => new ScreenId(10);   // 1以上。0 は None 予約
    // 既定は Layer => ScreenLayer.Base。Overlay/Modal にしたければ override
    protected override void OnShow() { /* Hub 購読の開始はここ。荷物は Payload で読める */ }
    protected override void OnHide() { /* 購読解除はここ */ }
}

// 2) 組み立て（フェーズの OnEnter か永続ルート）
var router = new ScreenRouter();
var uiSystem = new UISystem();
uiSystem.Initialize(hub, router, services);            // ここで命令の処理者になる
var screen = new GameObject("MyScreen").AddComponent<MyScreen>();
uiSystem.Register(screen);                             // 必ず UISystem.Register 経由（§5参照）

// 3) 表示は命令の発行だけ（どの基盤からでも）
hub.PublishCommand(new ShowScreenCommand(screen.Id));  // 既定 Push（Back で戻れる）
// 演出を使うなら毎フレーム: uiSystem.Tick(clock.UnscaledDelta);
// フェーズ退場時: uiSystem.Dispose();
```

### 実戦例1 — 出来事で更新する HUD（Hub 購読）

HP のように「変化した瞬間だけ知りたい値」は、`OnShow` で購読し `OnHide` で解除します。`Sample_HudScreen` の縮約版です。

```csharp
public sealed class MyHudScreen : Seed.UI.UIScreen
{
    public override ScreenId Id => Sample_ScreenIds.BattleHud;

    private IDisposable _subscription;                 // 購読の解除トークン
    private string _line = "";

    protected override void OnShow()
    {
        // Hub は UISystem.Register 時に Attach で配られている（自分で探さなくてよい）
        _subscription = Hub.Subscribe<CharacterDamaged>(OnDamaged);
    }

    protected override void OnHide()
    {
        _subscription?.Dispose();                      // 非表示中はイベントを受けない
        _subscription = null;
    }

    private void OnDamaged(CharacterDamaged message)
    {
        // 通知にはスナップショット値（RemainingHp/MaxHp）が同梱＝相手へ問い返さず自己完結
        _line = $"HP {message.RemainingHp}/{message.MaxHp}";
    }
}
```

ポイントは2つです。（1）通知には表示に必要な値が**スナップショットとして同梱**されているので、受けた側から戦闘ロジックへ問い返す必要がありません。（2）購読の寿命を OnShow〜OnHide に閉じ込めるので、非表示の画面がイベントを受け続ける事故が起きません。

### 実戦例2 — 毎フレームの連続値（Services 問い合わせ）

キャラの現在位置のように「毎フレーム滑らかに追う値」を Hub の通知にすると、毎フレーム全購読者へメッセージが飛ぶ無駄が出ます。これは `Services` から借りた問い合わせインターフェースを `Update` で読みます。

```csharp
public sealed class TargetMarker : Seed.UI.UIScreen
{
    public override ScreenId Id => new ScreenId(11);
    public override ScreenLayer Layer => ScreenLayer.Overlay;  // HUD の上に常駐

    private ICharacterQuery _query;
    private CharacterId _targetId;                     // 生成時に Construct 等で差し込む

    protected override void OnShow()
    {
        _query = Services.Resolve<ICharacterQuery>();  // キャラ基盤が貸し出している窓口
    }

    private void Update()                              // 追従表示は「艶」なので Update でよい
    {
        if (_query != null && _query.TryGetPosition(_targetId, out var position))
        {
            // position は HubVector3（X/Y/Z）。マーカーの座標をここで更新する
        }
    }
}
```

> 📖 **用語 — 艶（本プロジェクト固有）**: ゲームの真実（状態）に関与しない、見た目だけの要素。三大規約「状態は Tick、艶は Update」のとおり、表示の追従・演出は Update 側で行い、状態を変えないのが約束です。

使い分けの規約: **出来事（HP減少・アイテム取得）= Hub 購読、連続値（位置・ゲージ現在値）= Services 問い合わせ**。

### 実戦例3 — IScreenTransition を自作する（フェードイン）

演出は `IScreenTransition`（`IsDone` / `Tick(float)` / `Complete()` の3メンバ）を実装し、画面の `CreateShowTransition` / `CreateHideTransition` から返すだけです。

```csharp
/// <summary>CanvasGroup の alpha を 0→1 に上げるフェードイン。</summary>
public sealed class FadeInTransition : Seed.UI.IScreenTransition
{
    private readonly CanvasGroup _group;   // uGUI の透明度を一括制御するコンポーネント
    private readonly float _duration;      // 秒
    private float _elapsed;

    public FadeInTransition(CanvasGroup group, float duration)
    {
        _group = group;
        _duration = duration;
        _group.alpha = 0f;                 // 開始状態
    }

    public bool IsDone => _elapsed >= _duration;

    public void Tick(float deltaTime)      // Router が毎フレーム呼ぶ（実時間dt）
    {
        _elapsed += deltaTime;
        _group.alpha = Mathf.Clamp01(_elapsed / _duration);
    }

    public void Complete()                 // スキップ・割り込み時に Router が呼ぶ
    {
        _elapsed = _duration;
        _group.alpha = 1f;                 // 呼ばれた後は IsDone == true が契約
    }
}

// 画面側:
// protected override IScreenTransition CreateShowTransition()
//     => new FadeInTransition(_canvasGroup, 0.25f);
```

> 📖 **用語 — CanvasGroup**: uGUI のコンポーネント。配下の UI 全体の透明度（alpha）や入力の可否を1か所で切り替えられます。フェード演出の定番の足場です。

演出を使う場合は、毎フレーム `uiSystem.Tick(dt)` を呼ぶことを忘れないでください。デモでは `Sample_BattlePhase` がパイプラインの `TickPhase.Drain` で `uiSystem.Tick(_clock.UnscaledDelta)` を呼んでいます。**実時間 dt（UnscaledDelta）推奨**——ポーズ中でも画面演出は動けるようにするためです。

## 5. 仕組み

### Register が UISystem 経由でなければならない理由

`UISystem.Register(screen)` は2つのことをします。（1）`UIScreen.Attach(hub, services)` を呼び、画面が使う `Hub` / `Services` プロパティを配る。（2）`ScreenRouter.Register(screen)` で台帳へ載せ、`SetActive(false)` で初期非表示にする。`Attach` は internal なのでアプリからは呼べません。つまり `ScreenRouter.Register` を直接呼ぶと **Hub / Services が null のままの画面**ができてしまいます。正規ルートを1本にすることで、画面がデータへ到達する経路を基盤が保証しています。

### Show の内部（Base レイヤの場合）

`ScreenRouter.Show(id, transition, payload)` は画面自身が宣言するレイヤ（`UIScreen.Layer`）で分岐します。Base の場合:

1. 現在と同じ ID なら何もしない（連打で二重遷移しない）
2. `ClearAndShow` なら履歴を全消去
3. 前画面に `BeginHide`（`OnHide` は**即時**。抜け演出があれば表示は残す）
4. `Push` なら前画面 ID を履歴へ積む（上限 `MaxHistory = 32`。超過時は最古を捨てる）
5. 次画面に `BeginShow`（`SetActive(true)` → `OnShow` **即時** → 入り演出開始）

`Back()` は履歴の末尾を取り出して戻ります（このとき Payload は 0）。履歴が空なら false を返すだけです。

### 演出の駆動と「状態は即時、艶は後から」

`BeginShow` / `BeginHide` が返した演出は Router 内の進行リストに積まれ、`Tick(dt)` が完了まで進めます。重要なのは**状態変更（OnShow の購読開始・OnHide の購読解除）は演出の完了を待たず即時**なことです。抜け演出中の画面は GameObject が表示されたまま残り、演出完了時に Router が `Deactivate`（SetActive(false)）します——次の画面はもう出ているので、自然にクロスフェードになります。

演出中に同じ画面へ割り込みが入ったら（抜け演出中に Back で戻る等）、Router は進行中の演出の `Complete()` を呼んで終端へ飛ばしてから出直します。だから `Complete()` 後に `IsDone == true` を返すことが契約なのです。この仕様は `ScreenRouterTests` の `ReShowDuringHideTransition_CompletesItFirst` が緑で保証しています。

### 三大規約との関係

- **状態は Tick、艶は Update** — 画面の論理状態（どれが表示中か・履歴）は命令→Router で確定し、演出はそれに一切関与しません。演出を全部止めても遷移の結果は同じです
- **命令の処理者は1基盤** — `ShowScreenCommand` / `CloseScreenCommand` の処理者は `UISystem` だけ。`SubscribeCommand` を使っているため、誤って `UISystem` を2つ Initialize するとランタイムが二重処理者を検知して例外を出します
- **方針は App** — 「死んだらリザルトを出す」は UI 基盤にもキャラ基盤にも書かず、App の `Sample_ReactionPolicy`（`CharacterDied` 購読 → `ShowScreenCommand(Result, Replace)` 発行）が持ちます。決着後は HUD へ戻らないので Replace、という判断もゲームの方針だからです

> 📖 **用語 — フェイルファスト**: 不正な状態を検知したら即座に例外で止める設計方針。未登録 ID の Show・ID の二重登録が `HubException` になるのは、黙って動き続けて後で原因不明になるより、その場で構成ミスを知らせる方が安全だからです。

### よく使う部品のラッパー（SeedButton / SeedToggle / SeedSlider）

uGUI の Button などをそのまま使うと、画面の数だけ「連打対策・解除漏れ・SE 再生」が
散らばります。頻出部品は Seed のラッパー（`Assets/Script/UI/Runtime/Widgets/`）を使ってください。
**uGUI の各クラスを継承している**ので、既存プレハブへの差し替え（コンポーネントの置換）も、
コードからの `AddComponent<SeedButton>()` もできます。

| 部品 | 継承元 | 足しているもの |
|---|---|---|
| `SeedButton` | Button | 連打防止クールダウン / 処理中ロック（`BeginBusy`）/ `OnClick` が IDisposable / 長押し / 押下の沈み込み / SE フック |
| `SeedToggle` | Toggle | `OnValueChanged` が IDisposable / SE フック |
| `SeedSlider` | Slider | `OnValueChanged` が IDisposable / 任意刻み（`Step`。wholeNumbers は1刻み固定のため） |

```csharp
var button = buttonGo.AddComponent<SeedButton>();
button.OnClick(Buy).AddTo(_bag);          // Hub の購読と同じ書き味（OnHide で一括解除）
button.LongPressSeconds = 0.6f;
button.OnLongPress(ShowDetail).AddTo(_bag);

// 非同期処理の間は押させない（using で解除漏れなし）
async UniTaskVoid Buy() { using (button.BeginBusy()) { await PurchaseAsync(); } }

// SE の一元化（App の合成ルートで1回だけ）
SeedUiEffects.Interacted += _ => PlayClickSe();

// 値を「表示合わせ」するときは WithoutNotify（操作と区別＝設定画面を開いただけで
// 変更処理が走る事故を防ぐ）
toggle.SetIsOnWithoutNotify(saved.IsMuted);
```

すべてコードから制御できます（インスペクター運用も可能ですが、遷移・購読は
コード側に寄せるのが本プロジェクトの流儀です）。仕様はテスト
`UI/Tests/Editor/WidgetTests.cs`（12件）が保証します。

## 6. よくあるつまずき

- **症状**: 画面の `Hub` / `Services` が null で NullReferenceException
  **原因**: `ScreenRouter.Register` を直接呼んだ（`Attach` が呼ばれていない）
  **対処**: 登録は必ず `UISystem.Register(screen)` 経由にする

- **症状**: フェード演出がまったく進まない
  **原因**: `UISystem.Tick(dt)` を誰も呼んでいない
  **対処**: 合成ルートの毎フレーム処理に `uiSystem.Tick(clock.UnscaledDelta)` を追加する。演出を使わない画面だけなら呼ばなくても動きます（即時切替のまま）

- **症状**: `CloseScreenCommand` を発行したのに HUD（Base）が閉じない
  **原因**: Base レイヤは `Close` では閉じない仕様（false が返るだけ）
  **対処**: `Back()` か次の `Show` で遷移する。Close が閉じるのは Modal（最前面1枚）と Overlay（全部）だけ

- **症状**: `HubException: Screen#n は未登録の画面（Register漏れかIDの打ち間違い）`
  **原因**: Register 前に Show した、または ID 定数の打ち間違い
  **対処**: フェーズ OnEnter で Register してから `ShowScreenCommand` を発行する順番を確認

- **症状**: ゲージ表示のために毎フレーム通知を Publish していて重い
  **原因**: 連続値を Hub に流している（経路の選択ミス）
  **対処**: 出来事は Hub 購読、連続値は `Services.Resolve<ICharacterQuery>()` 等の問い合わせを Update で読む

- **症状**: モーダル表示中もキャラが動いてしまう
  **原因**: 基盤は入力を止めない（止めるかどうかはゲームの方針だから）
  **対処**: アプリ側が `router.ModalCount > 0` や `router.IsTransitionRunning` を見て入力処理をスキップする

- **症状**: プレハブから画面を出したいが基盤に読み込み API が無い
  **原因**: ロード戦略は意図的に基盤の外（プロジェクトごとに Addressables 等が違うため）
  **対処**: 外側でロード・Instantiate してから `UISystem.Register` する

## 7. 増やす・拡張する

- **新しい画面を足す**: ①アプリの定数クラス（`Sample_ScreenIds` 相当）に `public static readonly ScreenId MyScreen = new ScreenId(3);` を追記（1以上、既存と重複しない値）②`UIScreen` を継承して `Id` と `OnShow` / `OnHide` を書く ③合成ルートで生成して `UISystem.Register` → 表示したい場所で `ShowScreenCommand` を発行。手順はこの3点だけです
- **Overlay / Modal の画面にする**: 画面クラスで `public override ScreenLayer Layer => ScreenLayer.Modal;` と宣言します。閉じるのは `hub.PublishCommand(new CloseScreenCommand(ScreenLayer.Modal))`（引数省略時の既定も Modal）
- **出入り演出を付ける**: `IScreenTransition` 実装を作り、`CreateShowTransition` / `CreateHideTransition` から返す（§4 実戦例3）。null を返せば即時切替（既定）
- **出来事→画面遷移の方針を足す**: `Sample_ReactionPolicy` に倣い、「通知を購読して `ShowScreenCommand` へ変換する」純C#クラスを App 側に置きます。UI 基盤にもロジック基盤にも焼き込まないのがこつです
- **タイトルへ戻る**: `new ShowScreenCommand(TitleId, ScreenTransition.ClearAndShow)`。履歴が全消去されるので、タイトルから Back でインゲームへ戻る事故が起きません
- **遷移中の入力ロック**: `router.IsTransitionRunning` / `router.ModalCount` を公開プロパティとして用意してあるので、アプリの入力処理側で参照します
